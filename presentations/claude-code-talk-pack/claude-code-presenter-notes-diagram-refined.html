Claude Code: From Prompting to Engineering

Slide 1 of 20
1.5 min
PURPOSE
Set the frame: controlled engineering delegation, not prompt tricks.

Exact speaker notes

Good morning everyone. Before we start, a quick show of hands: how many of you have used an AI coding assistant?

Now keep your hand up if you have allowed one to read a repository, run commands, or edit several files on its own.

That second experience is what we are discussing today. Claude Code is not only a place where we ask coding questions. It can operate as an engineering agent inside a codebase.

My goal for the next hour is not to teach you twenty commands. I want to give you one working model that you can use from your first week here through senior-level engineering work: build shared context, make the plan visible, delegate inside clear boundaries, and verify the result with evidence.

The phrase I want you to remember is: the skill is not writing clever prompts. The skill is engineering the loop.

02

Chat gives answers. Agents take actions.

Diagram: Compare the two pipelines left-to-right. This slide benefits from a diagram because the difference is a change in flow: text-only response versus action/evidence loop.
Slide 2 of 20
1.5 min
PURPOSE
Explain why engineering discipline changes when the model can act.

Exact speaker notes

With a normal chat assistant, the basic unit is question and answer. I ask something, the model gives me text, and I decide what to do with it.

With Claude Code, the model can use tools. It can read files, search the repository, edit code, run a test command, inspect the output, and decide what to do next.

That changes the question we should ask as engineers. It is no longer only, 'Does this answer sound correct?' It becomes, 'What did the agent actually do? What was it allowed to do? What evidence do I have that the outcome is correct?'

This is why permissions, context, planning, tests and verification become more important—not less important—as the tool becomes more autonomous.

03

Context → decision → tool → result → repeat.

Diagram: Trace the loop clockwise and close it with the return arrow. The return path is the key idea: tool results become new context.
Slide 3 of 20
2 min
PURPOSE
Give the audience one small mental model before introducing feature names.

Exact speaker notes

I want to keep the architecture simple enough that you can hold it in your head while we work.

First is context: system instructions, persistent project or user instructions, what Claude has learned in this session, and the current task.

Claude reasons over that context and chooses a next action.

The action happens through a tool. Read and Search observe. Edit and Write change files. Bash executes commands. Agent delegates work. MCP can extend the available capabilities.

The tool result comes back into the conversation, becomes new context, and Claude chooses again. That repetition is the agent loop.

One control distinction matters already: instructions guide what Claude tries to do. Permissions are enforced by Claude Code and decide what tool actions it is allowed to do.

That is enough theory for now. Let us watch the loop on a tiny repository.

05

What just happened? The Context Ladder.

Diagram: The staircase is intentional. It shows progressive narrowing of attention rather than dumping the whole repository into context.
Slide 5 of 20
2 min
PURPOSE
Turn the live interaction into a reusable question-driven context workflow.

Exact speaker notes

What you just watched is a pattern I use often. I call it the Context Ladder.

ORIENT asks what this repository does and how to run it. MAP asks for the main modules and their responsibilities. LOCATE connects the task to the relevant module. TRACE follows data or control from input to output. CONSTRAIN asks what tests, invariants and dependencies protect that path. SUMMARIZE separates known evidence from inference, assumptions and risk.

The important idea is not to load the most context possible. Good context is relevant evidence plus the constraints and decisions that matter now.

Each question causes Claude to inspect the next useful part of the system. I can correct or narrow the explanation before we climb to the next rung.

By the time we plan a change, both Claude and I share a mental model of the relevant subsystem rather than a pile of unrelated repository text.

06

Put durable knowledge in the right layer.

Diagram: Point from the context sources into CURRENT CONTEXT. This clarifies source, ownership and persistence better than four independent cards.
Slide 6 of 20
2.5 min
PURPOSE
Clarify system instructions, user/project CLAUDE.md and repository-scoped auto memory after the audience has seen session context.

Exact speaker notes

Now we can separate the context we just built from the things that should be present every time.

System instructions come from Claude Code or its host. That is not where a normal repository convention belongs.

The user-level CLAUDE.md at ~/.claude/CLAUDE.md carries your own instructions across projects. People sometimes call this global memory informally, but the precise mechanism is user-level CLAUDE.md.

Project CLAUDE.md is team-shared repository context: architecture, build and test commands, conventions and project constraints.

Auto memory is different again. Claude writes those notes from corrections and discoveries. In current Claude Code it is scoped per repository and shared across worktrees, not one universal memory across all projects.

Both CLAUDE.md and auto memory are loaded as context. They guide behavior. They do not enforce security boundaries; permissions or hooks do that.

08

Research → Plan → Execute → Verify

Diagram: Point out the three human gates: ALIGN, APPROVE and ACCEPT. They show where judgment remains human.
Slide 8 of 20
1.5 min
PURPOSE
Introduce the operating discipline and human checkpoints.

Exact speaker notes

Here is the workflow for the rest of the session.

Research means build context, inspect the current behavior and find evidence.

Then the human aligns: are we solving the right problem and do we agree on the root cause?

Plan means make the proposed change visible before editing.

Then the human approves or changes the plan.

Execute is the phase where I am comfortable giving Claude more autonomy because the boundaries are now explicit.

Verify means collect evidence: diff, tests, acceptance criteria and residual risk.

The human then accepts—or rejects—the result.

So I do not describe this as removing the human from execution. I describe it as: the human controls the boundaries; Claude handles the mechanics.

09

Start read-only. Find evidence first.

Slide 9 of 20
1.5 min
PURPOSE
Teach a disciplined Research phase.

Exact speaker notes

In Research, I explicitly make the first request read-only when the task matters.

I want Claude to tell me the current behavior, the code path, the tests, the root cause and the likely change surface.

I also like to ask for four labels: KNOWN, INFERRED, ASSUMED and RISK.

KNOWN means the code or test proves it.

INFERRED means the explanation is supported but not directly proven.

ASSUMED means we have not verified it.

RISK means what could break if we act on this understanding.

This is a simple way to stop an attractive explanation from silently becoming a fact.

Live 02 — Investigate the bug

Slide 10 of 20
3.5 min
PURPOSE
Show root-cause research on the shopping calculator.

Exact speaker notes

Now I reveal the failure: for a two-thousand-rupee subtotal, a two-hundred-rupee fixed coupon and eighteen percent tax, the correct result is two thousand one hundred twenty-four, but the application returns two thousand one hundred sixty.

I will ask Claude to investigate without modifying files.

I expect it to trace the arithmetic. In the buggy code, tax is calculated on the full two thousand first, giving three hundred sixty. The fixed coupon is subtracted afterwards. That produces two thousand one hundred sixty.

The correct business rule is coupon first: two thousand minus two hundred gives eighteen hundred; eighteen percent tax on eighteen hundred is three hundred twenty-four; total two thousand one hundred twenty-four.

Then I ask the question that matters for engineering quality: why are our tests green? We should discover that the existing tests do not cover this fixed-coupon-plus-tax combination.

Before we plan, I ask Claude: 'What do you know, and what are you still assuming?'

Planning is where we expose scope, risk and verification before the repository changes.

I want the plan to say which files will change, what behavior will change, what will remain unchanged, what test will be added and what regression risk exists.

For a senior engineer, this is where you challenge architecture.

We have built context and identified the root cause. Now I want Claude to propose the route before it edits code.

I use /plan with the planning request. /plan is a convenience that puts Claude into Plan mode; the engineering value is that the approach becomes visible while change is still cheap.

13

Plan, /goal and /loop answer different questions.

Diagram: Use the three miniature loops to distinguish route control, finish-line control and time control. This is a conceptual comparison, so the diagrams materially reduce ambiguity.
Slide 13 of 20
2.5 min
PURPOSE
Correctly distinguish method, condition-driven completion and scheduled repetition.

Exact speaker notes

There are three ideas here and I want us to keep them separate.

The approved PLAN answers HOW. It contains the route: files, design, scope, tests and risks.

/goal answers WHEN DONE. Setting a goal starts a turn immediately. After turns, a separate evaluator judges the condition from what Claude has surfaced in the conversation. If the condition is not met, Claude keeps working and receives the evaluator reason as guidance for the next turn.

/loop answers WHEN AGAIN. It re-runs a prompt on an interval while the session stays open. For example: /loop 5m check if the deployment finished.

So /goal is condition-driven and /loop is time-driven. They are not interchangeable.

For the shopping-calculator bug I need the approved plan and /goal. I do not need /loop.

Live 04 — Execute the approved plan

Diagram: This is the most important control-loop diagram in the deck: approved plan → execute → evidence → goal check → repeat/stop, with a human-review escape path for material scope change.
Slide 14 of 20
4 min
PURPOSE
Demonstrate plan-constrained execution with /goal written as a measurable completion state.

Exact speaker notes

The human already approved the route. I am not asking Claude to plan again.

Notice the wording of the goal. It is a state that must become true: the approved plan is fully implemented without an unapproved scope or approach change, and the conversation contains evidence for each outcome.

I include concrete checks: coupon before tax, the exact two-thousand-rupee case, the regression test, unchanged percentage-discount behavior, and npm test exits zero.

That last detail matters because the /goal evaluator does not independently run commands or read files. It judges what Claude has surfaced into the conversation.

Setting /goal starts a turn immediately, so Claude can now edit, add the approved test, run the suite, inspect failures and correct implementation mistakes.

But a material change to the approved plan or scope is a human checkpoint. The goal text tells Claude to stop and ask rather than silently redesigning the work.

DEMO FALLBACK

Live 05 — Goal met ≠ change accepted

Diagram: Goal met feeds a human acceptance gate. Scope, tests, goal evidence and risk are the four verification inputs.
Slide 15 of 20
3 min
PURPOSE
Separate automated goal completion from explicit engineering verification and human acceptance.

Exact speaker notes

Suppose the /goal evaluator now says the condition is met. I still do not say, great, done.

The evaluator only judges evidence already surfaced in the conversation. It does not independently inspect the repository or run tools.

My verification pass therefore checks the actual diff against both the approved plan and the goal.

I ask for scope conformance, how each plan step was implemented, the regression test and full suite result, evidence for each goal condition, and anything still untested, assumed or risky.

I explicitly say not to make more changes during this verification. If we discover a material issue, the human decides whether to return to Research, Plan or Execute.

Claude Code also has a /verify skill that can build, run and observe an application rather than relying only on tests. That can be useful, but it does not replace the broader engineering checks I am teaching here: plan conformance, scope, tests, goal evidence and residual risk.

Only after looking at the evidence do I accept or reject the change.

LIVE ACTION
Run the read-only verification prompt. Inspect the diff and test evidence with the audience. End with an explicit human decision.
DEMO FALLBACK
If time is short, show the relevant diff, the new regression test and the full test result, then state the remaining verification questions verbally.

Separate work when separation helps.

Diagram: The topology shows context isolation. Emphasize downward delegation and upward summary/evidence return.
Slide 17 of 20
1.5 min
PURPOSE
Teach subagents as context isolation plus specialization.

Exact speaker notes

I primarily think of subagents as context-management and specialization tools.

Suppose I ask Claude to investigate fifty files. If all of those reads happen in my main session, I may fill the context with details that I only needed temporarily.

A subagent can do that exploration in its own context window and return a concise summary.

Custom subagents can also have their own focused system prompt, their own tool access and independent permissions. That is useful for roles such as a read-only reviewer, a test-coverage reviewer or a domain-specific investigator.

Use agents when separation provides value. Do not create multiple agents just because multiple agents sound impressive.

Use the right layer for the right guarantee.

Diagram: Keep the existing guardrail layers. It already expresses increasing enforcement strength; another diagram would add noise.
Slide 18 of 20
2 min
PURPOSE
Clarify guidance, permissions, hooks and organization policy.

Exact speaker notes

There are different kinds of control, and they should not be confused.

CLAUDE.md is guidance: please work this way.

Permissions are an approval boundary: allow this tool action, deny it, or ask me first.

Hooks run at lifecycle events. A deterministic hook can say: after an edit, run the formatter; before a dangerous command, block it; when Claude needs input, notify me.

The official docs explicitly describe hooks as deterministic control for things that should always happen rather than relying on the model to remember.

And above all of this is our organization policy: approved repositories, credentials, customer data and external services.

More autonomy should mean stronger boundaries and stronger verification—not weaker governance.

Preserve the signal. Remove the noise.

Diagram: Use the before/after compaction diagram first; then use the command list as reference.
Slide 19 of 20
1.5 min
PURPOSE
Teach context hygiene, compaction and practical handoff.

Exact speaker notes

Context is finite, and long sessions accumulate both signal and noise.

Use /context to inspect what is consuming the window.

Claude Code automatically manages context as it fills, and /compact lets us deliberately replace older history with a structured summary.

There is a subtle but useful detail: system instructions stay in place, project-root CLAUDE.md and auto memory are re-injected after compaction, while some dynamically loaded context may have to be rediscovered later.

This is why I like an explicit handoff or compact instruction for important work. Preserve the goal, acceptance criteria, our current architecture understanding, decisions and evidence, files changed, verification status and open risks.

That lets the next session—or the next engineer—start with the useful reasoning state instead of replaying the entire conversation.

Exact speaker notes

If you remember only four things from today, remember these.

Build shared context before asking for an important change. Research from evidence before you design.

Make the plan visible and review it while change is cheap.

Delegate execution inside explicit tool, permission and policy boundaries. Use /goal for a condition-driven finish line; use /loop for scheduled repetition, not as a substitute for the goal.
